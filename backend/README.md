# Legal Metrology Extraction Service

Team 1's authoritative pipeline. Package photographs in, a provenance-bearing
`PackageFactSnapshot v1.1` out.

**Boundary.** This service owns capture ingestion, image processing, OCR,
observation construction, normalization, fact reconciliation and snapshot
generation. It does **not** own legal applicability, compliance rules, verdicts
or decision traces — those belong to the compliance engine. No endpoint here
returns a PASS/FAIL, and the statuses it does return describe this pipeline's
state, not a package's compliance.

---

## Quick start

```bash
cd backend
pip install -e ".[dev]"      # contract layer + tests, no heavy engines
pytest                        # 160 tests, ~9s, no external services
python scripts/demo.py        # see a real snapshot come out of the pipeline
```

The base install deliberately excludes PaddleOCR and OpenCV. The contract rules
— projection, quarantine, fact resolution, normalization — are the part that
must be correct, and they should be testable on any machine in seconds. The
engines are extras.

### `scripts/demo.py`

A verification tool rather than a test: the tests assert, this one shows. It
runs four packages through the real pipeline with a scripted recognizer and
prints every fact with its status, value and provenance trail — then the typed
projection generated from those facts.

The four scenarios each demonstrate a rule that is easy to get wrong: a normal
two-view package, panels that disagree on the MRP, a package nothing could be
read from, and a unit price that is derived rather than printed. Everything
after recognition is the production code path.

### Running the service

```bash
pip install -e ".[cv,tesseract]"   # image diagnostics + the baseline OCR
uvicorn app.main:app --reload
open http://localhost:8000/docs    # interactive OpenAPI
curl localhost:8000/v1/health
```

`/v1/health` reports `degraded` until an OCR engine is installed and the
quality policy is calibrated, and lists exactly what is wrong. That is the
intended behaviour, not a misconfiguration: a service that reported `ok` while
running on uncalibrated thresholds would be lying about what its verdicts mean.

## The four-endpoint contract

```
POST /v1/capture-sessions             open a session, register the declared context
POST /v1/artifacts                    upload one image + its metadata bundle
POST /v1/extraction-jobs              extract facts from the session's artifacts
GET  /v1/extraction-jobs/{id}/snapshot        the released PackageFactSnapshot
GET  /v1/extraction-jobs/{id}/observations    the full evidence trail
GET  /v1/quarantine                   runs awaiting engineering review
```

All three write endpoints are idempotent on the client-minted identifier. The
mobile upload queue retries after responses it never saw, so a repeat is the
ordinary case, not an error.

## The five rules this code enforces mechanically

These are Team 2's frozen ruling, expressed as code rather than convention.
Each has tests in `tests/test_contract_rules.py` that name the rule they defend.

**1. `facts[]` is the only authoritative source.** Top-level typed fields are
generated by `PackageFactSnapshot.project()` from the fact set. No extraction
code writes them.

**2. A projection/facts divergence quarantines the run.** It is never repaired
in place — a validator that fixed the mismatch would make the bug invisible.
`QuarantinedRun` records the specific divergences and no snapshot is released.

**3. `DECLARED_ABSENCE` can never be manufactured from OCR non-detection.**
`ResolvedFact.declared_absent()` demands a written evidence basis and refuses
without one. A field with no candidates resolves to `UNKNOWN`. This is the rule
with the most downstream consequence and the easiest to break by accident.

**4. UNKNOWN / DECLARED_ABSENCE / CONFLICTING project to `null`,** while the
status survives in `facts[]`. A null projection is a presentation of a resolved
state, not a collapsed one.

**5. An observed declaration is never overwritten by a computed one.** A
printed unit sale price stays `OBSERVED`; a calculated one is `DERIVED` with a
trace to both source facts, and only appears where nothing was printed.

## ⚠️ What is NOT ready for production

Three things, stated plainly because each would otherwise look finished.

### 1. The quality thresholds are guesses

Every number in `QualityPolicy` is a plausible starting value, not a calibrated
one. `calibrated=False` is the shipped default; the runner logs a warning on
every run, `/v1/health` reports `degraded`, and each run's diagnostics carry
the caveat.

A RETAKE verdict from this policy is **advisory**. Do not treat it as an
acceptance criterion until `benchmark/harness.py --calibrate` has fitted the
cutoffs against measured extraction failure. That needs the dataset below.

### 2. No OCR engine has been selected

PaddleOCR PP-OCRv5 is the primary *candidate*, chosen from documented language
coverage (Devanagari, Hindi, Marathi, Tamil, Telugu, English). That is a
hypothesis with good documentation, not a measurement. Tesseract is wired as a
transparent baseline. Nothing is selected until the benchmark runs.

### 3. The ground-truth dataset does not exist — and this is the blocker

`benchmark/harness.py` is complete and cannot produce a number, because there
is nothing to measure. It needs real photographs of real Indian retail
packaging, annotated per region with the text, the field, the normalized value
and the geometry — including the conditions that actually break extraction:
glare on foil, curved bottles, tiny regulatory print, mixed Devanagari/Latin
panels, shop-aisle lighting.

That is field work, not code. Until it exists:

- every threshold in this repo stays a guess,
- no engine can be selected,
- the benchmark harness reports that it has nothing to measure rather than
  producing a number that looks like a result.

This is the single highest-value next task, and it gates phases 5, 10 and 11 of
the implementation plan.

## Physical text-size measurement: deliberately not implemented

Rule 7 sets minimum letter heights against the principal display panel's area.
Checking that needs millimetres; a bounding box gives pixels; the conversion
needs a validated scale that an uncontrolled handheld photograph does not
provide.

So `assess_measurability()` returns `NOT_TESTABLE` and the resolver emits an
explicit fact saying so, rather than staying silent. A focal length in the EXIF
is **not** a scale — without subject distance it says nothing about millimetres
per pixel, and the code refuses to treat its presence as enabling measurement.

`physical_measurement.py` is where a calibrated capture mode plugs in when one
is built. It must clear an accuracy acceptance gate — including a demonstrated
error bound — before anything it produces becomes compliance-relevant evidence.

## Auditability

Every authoritative fact answers §18's four questions:

- **Which pixels?** `provenance.geometry`, in original-image coordinates, with
  `TransformChain` mapping back from any crop or rectification.
- **Which OCR run?** `provenance.ocr_run_id`, resolving to engine, model id,
  model version and language set.
- **Which normalization rule?** `normalization_rule` on the candidate.
- **Which resolver decision?** The fact's `note`, plus every rejected reading
  retained on the fact and every candidate in the observation store.

Two hashes, answering different questions:

- `content_hash()` — the exact document, for §16's integrity control.
- `semantic_hash()` — what the snapshot *claims*, ignoring per-run ids. Stable
  across reruns, so a regression suite can detect when a model or threshold
  change moved the result.

## Known gaps

- **Alembic.** `create_all` is fine now and cannot express a column change.
  Move before the first schema change lands on a database holding real
  evidence.
- **Async workers.** Extraction runs synchronously. The response shape is
  already the asynchronous one, so moving the body onto a worker changes
  nothing the client sees.
- **Rectification.** The transform-chain machinery is built and tested; no
  stage populates it yet, because engines currently receive the original image.
  Curved and perspective-distorted text is where this will earn its place —
  and §9 requires benchmarking whether rectification actually improves
  recognition before asserting it does.
- **ML Kit script coverage.** The on-device assist reads Latin and Devanagari.
  Tamil and Telugu have no ML Kit model, so the mobile legibility check
  under-reports on those panels. The server stack reads both; this is why a
  mobile `fail` is a prompt to the inspector and never a finding.
